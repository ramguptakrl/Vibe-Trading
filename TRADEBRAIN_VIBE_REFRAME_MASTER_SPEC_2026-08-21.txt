VIBE-TRADING REFRAME / MASTER IMPLEMENTATION SPEC
=================================================

DOCUMENT PURPOSE
----------------
This file is the canonical reframing instruction for adapting the upstream
HKUDS/Vibe-Trading repository to the owner's TradeBrain + BSE Decision Engine
philosophy WITHOUT rewriting or deleting the useful Vibe-Trading framework.

This is an OVERLAY / GOVERNANCE / INTEGRATION SPEC, not a request to fork every
upstream idea into custom code.

Primary rule:

    KEEP VIBE-TRADING WHERE IT IS STRONG.
    ADD TRADEBRAIN WHERE INDIAN-MARKET IDENTITY, PROVENANCE, MEMORY AND RESEARCH
    CONTINUITY ARE STRONGER.
    LET THE BSE DECISION LAYER CONTROL FINAL TRADING GUIDANCE.
    NEVER LET AN LLM, INDICATOR, SWARM, OR GENERIC REPO DEFAULT BYPASS HARD RULES.

The desired system is not "replace Vibe-Trading with my old software."

The desired system is:

    VIBE-TRADING PLATFORM
        + TRADEBRAIN INDIAN MARKET KNOWLEDGE / MEMORY / PROVENANCE
        + BSE-SPECIFIC DECISION / RISK / LEARNING POLICY
        = ONE EVIDENCE-DRIVEN PERSONAL TRADING RESEARCH SYSTEM

The repository may retain its multi-market capabilities, finance skills,
backtesting engines, swarms, factor research, options tools, Shadow Account,
CLI/API/frontend, and other useful upstream features.

The owner's custom rules should be activated through a specific profile / mode,
not by destructively changing every global upstream behavior.

SOURCE IDEOLOGY BEING MERGED
----------------------------
A. TRADEBRAIN
   A local-first Indian financial intelligence system that progressively learns:
   - NSE/BSE/SEBI/RBI/NSDL/CDSL/MoSPI/AMFI context.
   - security identity.
   - issuer/company identity.
   - corporate events.
   - documents/filings.
   - prices and market structure.
   - fundamentals.
   - research hypotheses.
   - backtests and outcomes.
   - portfolio/risk.
   - broker rules.
   - persistent thesis memory.

   Key TradeBrain principles:
   - Local memory first.
   - Preserve source, timestamp, provenance and hashes.
   - Archive raw payloads before normalization where practical.
   - LLM is reasoning/orchestration, not the market-data source of truth.
   - Exchange symbol is not company identity.
   - ISIN is the cross-exchange security identity.
   - Issuer/company entity sits above security/listing identity.
   - Missing from a source is not proof of delisting.
   - Research intelligence and broker execution remain separate.
   - Secrets remain outside code.
   - Indian equities are the core subject.

B. BSE DECISION ENGINE
   A BSE Ltd-focused evidence engine designed to answer:
       "What is the best defensible action now, given market structure,
        risk, history, context and the user's hard constraints?"

   It is NOT:
       indicators -> BUY/SELL

   Its intended flow is:
       MARKET DATA
       + INTELLIGENCE
       + HISTORY / ANALOGUES / OUTCOMES
       -> MARKET STRUCTURE
       -> RISK / CRASH GUARD
       -> HARD RULE ARBITER
       -> DAY or SWING candidate
       -> FINAL GUIDANCE

   Key BSE Engine principles:
   - AI is one input, not the engine.
   - Final product is advisory unless the owner explicitly changes the goal later.
   - Hard safety rules cannot be learned away.
   - Useful information should be measured, not automatically converted into rigid rules.
   - Adaptive values and learned values are not the same thing.
   - Historical evidence should determine which information deserves weight.
   - Current model A must be compared against challenger B before promotion.
   - Out-of-sample / walk-forward validation is required for learned changes.
   - Never optimize only for one crash date or one favorable period.
   - False positives matter.
   - Preserve old data/history through architecture changes.

5. HARD RULES FOR THE BSE DECISION PROFILE
======================================================================

These are NOT learnable parameters.

5.1 ADVISORY BOUNDARY
- AUTO_EXECUTION = OFF.
- The profile must not invoke live order-placement tools.
- Final output is guidance only.
- Research and execution remain separate.

5.2 DAY TRADE MODE
- Same-session trade mode.
- LONG or SHORT may be considered.
- A fresh candidate requires explicit entry, TP and SL.
- LONG geometry:
      SL < Entry < TP
- SHORT geometry:
      TP < Entry < SL
- DAY positions must be flat before 15:15 IST.
- 15:15 IST is a user hard cutoff.
- If the verified exchange close is earlier, the earlier verified close prevails.
- Do not learn away the cutoff.
- The engine must be willing to output NO TRADE / WAIT.
- "Market is bearish" does not automatically authorize SHORT.
- A short must independently qualify.

5.3 SWING / POSITION MODE
- Longer-duration equity holding.
- Current profile is LONG-only.
- MTF is a funding mechanism, not the retired L1/L2/L3 rescue architecture.
- Approx. 1:3 R:R is a starting preference only.
- It is NOT immutable.
- Severe Crash Guard blocks new SWING/MTF long exposure.
- A true recommendation must eventually account for net economics:
      own contribution,
      broker-funded amount,
      days held,
      MTF interest,
      brokerage,
      STT,
      exchange/transaction charges,
      SEBI fees,
      GST,
      stamp duty,
      DP/pledge-related charges where applicable,
      slippage,
      true break-even,
      true net target.
- Until this cost engine is verified, label Swing economics as GROSS / INCOMPLETE.

5.4 RETIRED ACTIVE STRATEGY
Do not revive as the active strategy:
- Probe / L1 / L2 / L3 rescue cycle.
- Rescue averaging as the core architecture.
- Old approx. -₹100,000 cycle kill logic.
- Post-kill 1-share recovery probe.
- Old fixed +₹45 analogue metric as a current target rule.

Legacy records may remain for history/audit/research.

6. HARD RULE ARBITER
======================================================================

There must be one authoritative final policy gate.

Suggested flow:

    candidate evidence
        -> data-quality gate
        -> session/time gate
        -> instrument/broker/exchange gate
        -> portfolio/capital gate
        -> Crash Guard / severe risk gate
        -> mode-specific geometry gate
        -> advisory-only gate
        -> final verdict

Possible verdict classes:
    LONG_CANDIDATE
    SHORT_CANDIDATE
    WAIT
    NO_TRADE
    EXIT_REQUIRED
    DATA_INSUFFICIENT
    BLOCKED_BY_HARD_RULE

Fail closed when:
- required data is stale/missing/contradictory,
- instrument identity is unresolved,
- broker/exchange rule is unknown where required,
- costs are required but cannot be computed reliably,
- time/session state is uncertain near a hard cutoff,
- safety state is inconsistent.

Never convert missing data into false confidence.

7. ADAPTIVE VS LEARNED
======================================================================

Use these terms precisely.

ADAPTIVE:
    Automatically recomputed from current data.

Examples:
- support/resistance.
- ATH/comparable highs.
- swing highs/lows.
- EMA levels.
- current volatility.
- current regime.
- live multi-timeframe structure.

LEARNED:
    Historical outcomes change the reliability, probability, importance,
    weighting or candidate thresholds.

Examples:
- support type reliability.
- timeframe usefulness.
- false-break probability.
- Crash Guard threshold quality.
- expected time-to-target.
- setup-family success rates.
- analogue feature weights.
- candidate DAY R:R floor.
- preferred Swing target geometry.

Never label a hand-tuned or automatically recomputed number as "learned."

10. CRASH GUARD
======================================================================

Crash Guard is a risk gate.

It may use combinations such as:
- short-term price decline.
- drawdown from intraday high.
- abnormal volume.
- major support failure.
- multi-timeframe bearish alignment.
- failed ATH breakout/rejection.
- market-wide stress context.
- BSE-specific weakness vs index/systemic weakness.

Rules:
- Severe state can block fresh DAY LONG.
- Severe state can block fresh SWING/MTF LONG.
- Severe state does not automatically create a SHORT.
- A SHORT must qualify independently.
- Thresholds are provisional until replayed/calibrated.
- Test severe days AND ordinary days.
- Explicitly measure false positives.
- Avoid optimizing to a single known crash session.


======================================================================
11. TRADEBRAIN INDIAN IDENTITY MODEL
======================================================================

Do not treat symbols as the canonical company identity.

Required model:

    Company / Issuer Entity
        -> Canonical Security (ISIN)
            -> Exchange Listing(s)

For India:
- use ISIN as cross-exchange security identity where applicable.
- keep exchange + symbol/scrip code as listing identity.
- do not merge securities only because names look similar.
- do not fuzzy-link corporate events without strong evidence.
- prefer:
      exact exchange symbol,
      exact ISIN,
      exchange security ID,
      verified issuer alias,
      official exchange metadata,
      document/attachment identifiers.

Missing from a current feed does not prove delisting.

For BSE Ltd itself:
- resolve canonical security through official/current security master.
- do not hardcode a stale identifier in business logic if the security master can resolve it.


======================================================================
12. SOURCE / PROVENANCE POLICY
======================================================================

Every important evidence item should be capable of carrying:
- source name.
- source URL / endpoint where applicable.
- retrieval timestamp.
- market/event timestamp.
- raw archive path where applicable.
- normalized record ID.
- SHA-256 or equivalent content hash when practical.
- parser/version where relevant.
- entity/security linkage confidence/method.
- freshness status.
- transformation lineage.

Raw official payloads should be archived before normalization where practical.

LLM summaries must point back to source evidence.

If a web/news claim affects a trading candidate:
- store the headline/source/time.
- distinguish primary/official source from secondary reporting.
- avoid treating repeated copies of one story as independent evidence.

Source truth priority for Indian corporate/reference facts should favor official
NSE/BSE/SEBI/RBI and other authoritative sources over commentary.

13. CORPORATE EVENT + DOCUMENT MEMORY
======================================================================

TradeBrain-style event flow:

    official/reliable event source
        -> raw archive
        -> parser
        -> normalized event
        -> exact entity/security link where possible
        -> attachment/document download
        -> hash/dedup
        -> document understanding
        -> "what changed?" research queue
        -> BSE relevance scoring
        -> historical outcome linkage

Do not use dangerous fuzzy guessing to force 100% entity linkage.

The engine should know the difference between:
- event received,
- event linked,
- document downloaded,
- document parsed,
- event summarized,
- relevance assessed,
- historical effect studied.


======================================================================
14. RESEARCH / HYPOTHESIS LIFECYCLE
======================================================================

Reuse Vibe-Trading research goals, hypotheses, SDM and factor tooling.

But use this BSE-specific lifecycle:

    IDEA
      -> HYPOTHESIS
      -> IMPLEMENTED CANDIDATE
      -> IN-SAMPLE REPLAY
      -> OUT-OF-SAMPLE / WALK-FORWARD
      -> COST/SLIPPAGE STRESS
      -> REGIME TEST
      -> FALSE-POSITIVE REVIEW
      -> CHALLENGER
      -> PROMOTED
      -> MONITORED
      -> DECAYED / RETIRED if evidence deteriorates

Never silently promote a hypothesis because:
- one backtest is profitable,
- Sharpe > a generic threshold,
- an LLM likes it,
- a paper says it works elsewhere,
- it performs on only one period,
- it detects one famous crash.

Generic Vibe SDM thresholds remain useful diagnostics.
They are not sufficient for BSE-specific promotion.


======================================================================
15. CONTROLLED LEARNING / CHAMPION-CHALLENGER
======================================================================

For any learned change:

1. Preserve current model A.
2. Create challenger B.
3. Record exactly what changed.
4. Replay both on identical data.
5. Verify no look-ahead leakage.
6. Include realistic costs/slippage.
7. Compare:
   - return / expectancy,
   - hit rate,
   - profit factor,
   - drawdown,
   - MAE/MFE,
   - TP-first vs SL-first,
   - time-to-target,
   - false positives,
   - trade frequency,
   - regime stability,
   - stability across subperiods.
8. Run out-of-sample or walk-forward.
9. Report benefits AND tradeoffs.
10. Promote only deliberately.
11. Write promotion decision to audit/research history.
12. Never modify hard owner rules through learning.

No autonomous self-rewriting of production policy.

======================================================================
19. CONFIDENCE / RELIABILITY LANGUAGE
======================================================================

Avoid fake precision.

Separate:
- DATA QUALITY.
- RULE STATUS.
- HISTORICAL RELIABILITY.
- CURRENT SETUP QUALITY.
- MODEL UNCERTAINTY.

A confidence number is allowed only if its calibration method is defined.

Prefer labels such as:
    HIGH EVIDENCE
    MODERATE EVIDENCE
    LOW EVIDENCE
    INSUFFICIENT DATA

When showing learned probabilities:
- include sample size.
- include time window.
- include regime/setup definition.
- include out-of-sample status.
- do not present illustrative statistics as production statistics.

- do not add an indicator just because it exists.

======================================================================
21. OPERATING MODES / SCHEDULE
======================================================================

Use the verified Indian exchange calendar/session as the clock source.

A useful operating model:

A. MARKET-ACTIVE MODE
   During the trading session:
   - prioritize live data freshness.
   - maintain BSE structure/context.
   - update Crash Guard.
   - update DAY/SWING candidate state.
   - monitor official material events/news.
   - minimize expensive experimental work that can interfere with live analysis.
   - produce advisory guidance only.

B. DAY EXIT WINDOW
   - enforce the owner's DAY cutoff.
   - no new DAY candidate near/after the configured exit window.
   - at/after 15:15 IST, any DAY holding is invalid and guidance must be EXIT_REQUIRED.

C. AFTER-MARKET STUDY MODE
   After session close:
   - finalize candles.
   - reconcile stored vs live data.
   - ingest the day's corporate events/documents.
   - score actual candidate outcomes.
   - run replay/backtests.
   - test challengers.
   - update research queues.
   - generate post-mortems.
   - do not silently promote models.

D. OFF-HOURS / DEEP RESEARCH
   - historical backfill.
   - filings/document analysis.
   - factor/paper research.
   - data-quality audits.
   - decay monitoring.
   - archive verification.

Reuse Vibe scheduled-research plumbing where possible.

28. DEFINITION OF "FINAL RESULT MUST FOLLOW MY IDEAS"
======================================================================

This means:

The repository can keep its own tools, research approaches and broad capabilities.

However, when the user asks the TradeBrain/BSE profile:

    "What should I do with BSE now?"
    "Is there a DAY trade?"
    "Is there a Swing entry?"
    "Should I wait?"
    "Why is BSE weak?"
    "What does history say?"

the final BSE answer must be produced through THIS governance chain:

    VERIFIED DATA / SOURCE EVIDENCE
        + TRADEBRAIN IDENTITY / MEMORY
        + VIBE RESEARCH / FACTOR / BACKTEST CAPABILITIES
        + CORPORATE / NEWS / MACRO CONTEXT
        + BSE MARKET STRUCTURE
        + BSE HISTORICAL OUTCOMES
        + BSE LEARNED RELIABILITY
        -> HARD RULE ARBITER
        -> FINAL ADVISORY GUIDANCE

No individual Vibe skill, alpha, agent, indicator or generic strategy template
may skip this chain and declare the final BSE action by itself.

32. CANONICAL SHORT FORM
======================================================================

BUILD ON VIBE-TRADING, NOT AGAINST IT.

Vibe-Trading provides the broad machine:
    tools + UI + API + backtests + factors + research + agents + governance.

TradeBrain provides the Indian memory:
    identity + official sources + provenance + events + documents + continuity.

BSE Decision Engine provides the final discipline:
    structure + Crash Guard + DAY/SWING policy + hard rules + BSE outcomes
    + controlled learning + advisory verdict.

The final objective is not the maximum number of indicators, agents or trades.

The final objective is:

    THE MOST DEFENSIBLE BSE DECISION THE AVAILABLE EVIDENCE CAN SUPPORT,
    WITH HARD SAFETY RULES, TRACEABLE SOURCES, HONEST UNCERTAINTY,
    AND A LEARNING PROCESS THAT MUST PROVE IMPROVEMENT BEFORE IT CHANGES
    PRODUCTION BEHAVIOR.
